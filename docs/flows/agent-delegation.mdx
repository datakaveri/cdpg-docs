## Why two checks instead of one

A single check — "does this agent have access?" — would let an agent outlive the authority it borrowed. If the user loses access to a dataset, an agent holding its own independent grant would keep working.

Requiring the user's permission *and* the delegated permission makes the agent's authority genuinely derivative:

| Change | Effect on the agent |
| --- | --- |
| The user loses access to the resource | The agent loses it too, immediately — the user's check now fails |
| The delegation is revoked | The agent loses it; the user is unaffected |
| The agent is granted a new resource | Nothing happens unless the user also has it |
| The agent is suspended | Everything stops, regardless of tokens or grants |

## What the agent never holds

- **Credentials** — attached at the MCP Gateway boundary, after the plan is fixed.
- **An open API surface** — only declared tools, with validated arguments.
- **Authority to spend** — consequential operations require a human.
- **Its own standing** — every permission is borrowed and independently revocable.

## Prompt injection and untrusted data

Data returned from the exchange is wrapped and marked as untrusted before it reaches the model. A dataset description, a discussion comment, or a file's contents are things the agent may *summarise* — never instructions it may follow. Without this boundary, any provider who can write a resource description could steer any agent that reads it.
