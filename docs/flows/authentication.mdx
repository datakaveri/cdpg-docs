## Why identity is centralised at the gateway

Internal components receive identity as trusted, signed headers and contain **no credential-handling logic at all**. Adding a new authentication method (or rotating keys) touches only the edge. An invalid header signature is always a hard `401` — it never falls back to another path — and the issued-at timestamp bounds replay.

## Delegation in detail

An application acting for a user can never do more than *either* the delegating user *or* the delegation itself allows:

1. The user records a delegation to the app (scoped: which resources, which actions).
2. The app calls the platform identifying both itself and the user it represents.
3. The gateway verifies the delegation with the [User Service](../components/user-service.md) and forwards the **user's** identity, narrowed to the intersection of the user's rights and the delegation's scope.

See the [Auth Flow API reference](../api-reference/auth-flow.md) for the exact claims and headers, and the [JWT Validation guide](../guides/jwt-validation.md) for debugging.
