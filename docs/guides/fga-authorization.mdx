# Relationship-Based Authorization

How the platform answers **"may this subject perform this action on this resource?"**

Access is **relationship-based** (ReBAC). Rather than attaching a permission list to each user, the platform stores relationships between subjects and resources and answers a permission question by traversing them.

That choice is what makes organisational access practical. A grant to a hundred-person institution is *one* grant, not a hundred — and someone joining or leaving that institution gains or loses access without a single policy being rewritten.

Three roles, deliberately separated so that recording, deciding, and enforcing are distinct concerns:

| Role | Component | Responsibility |
| --- | --- | --- |
| **PAP** — administration | [Policy Service](../components/policy-service.md) | The durable record of every grant, with its expiry and constraints |
| **PDP** — decision | [Authorization Service](../components/authorization-service.md) | Answers the permission question; stores none of the data it protects |
| **PEP** — enforcement | Gateway, services, data planes | Acts on the decision, at the point that has enough context |

The reason for the split is that no single component has both the authority and the context. A gateway cannot filter rows out of a geospatial query; a data plane should not be reimplementing policy semantics.

## From grant to decision

A grant is authored once and projected into the relationship graph asynchronously. Writing the grant and its event in **one transaction** is what makes the projection trustworthy: a committed policy always has an event, and a rolled-back one never emits a phantom grant.

Delivery is at-least-once, so the projection is idempotent and versioned — a redelivered or out-of-order event cannot produce a wrong result.

### Creation and revocation are not symmetric

This asymmetry is intentional, and it is the thing most worth understanding about the pipeline:

| Change | While the projection catches up | Why |
| --- | --- | --- |
| **New grant** | Access is denied | A false denial is safe, and the client can retry |
| **Revocation** | Applied to the decision path first; graph cleanup follows | A delayed revoke means continued unauthorized access |
| **Expiry** | Enforced at decision time, on the service's own clock | Correct even if no cleanup job has run |

A grant that has passed its expiry stops working at that instant — not when a sweeper next runs.

## Subjects

| Subject | Reaches |
| --- | --- |
| `user` | that person |
| `organisation` | its members, through membership relationships |
| `group` | a named set of users within an organisation |
| `application` | a registered machine client |
| `agent` | an AI agent — only ever in combination with its delegating user |

### Grant shapes

| Policy type | Relationships written |
| --- | --- |
| **Individual** | one relationship from the named consumer to the resource, per access type |
| **Group** | one per allowed user, plus one per allowed organisation — organisation members are reached *through* the graph rather than expanded into individual grants |

Access types (`api`, `file`, `sub`) are validated against what the resource actually supports, so a grant cannot confer an access mode the resource does not offer.

## Agent access

An agent request is checked **twice**, and both must pass:

```text
the delegating user's own permission on the resource
  AND the agent's delegated permission on that same resource
  AND the delegation is active and unexpired
  AND the kill switch permits this agent
```

The delegated relationship is separate from the user's, which is what keeps an agent strictly narrower: revoking the delegation removes the agent's access and leaves the user's intact. See the [Agentic Plane](../technical/agentic-plane.mdx).

## Where enforcement happens

A central decision is not the end of enforcement:

| Point | Can decide |
| --- | --- |
| **Gateway** | Authentication, which operation is called, relationship checks on a resource named in the request, call-rate limits |
| **Service** | Resources that only become known once the body is parsed or a lookup runs |
| **Data plane** | Query- and result-dependent constraints — which rows may be returned, which fields must be withheld, how much data a grant permits |

When a decision carries an instruction the receiving component cannot apply, the request is **denied** rather than served without it. Silently ignoring part of a policy is the one outcome the design does not permit.

## Troubleshooting

**A grant was created but access is still denied.** The projection has not caught up, or the event never left the Policy Service. Check the outbox for unsent rows — if they accumulate, the messaging backbone is unreachable and the dispatcher is retrying.

**Access is denied unexpectedly.** Work outward: confirm the grant exists and is active, confirm it has not expired, confirm the access type matches the operation, then confirm the relationship exists in the graph. For an organisation grant, check the user's **membership** relationship — that is the most common gap, and it fails in a way that looks like the grant itself is broken.

**An agent is denied where the user succeeds.** Expected when the delegation does not cover that resource or access type, has expired, or the agent is suspended. The two checks are independent by design.

**Duplicate events.** Safe. The projection deduplicates by event identity and compares versions, so redelivery cannot double-apply or resurrect a revoked grant.
